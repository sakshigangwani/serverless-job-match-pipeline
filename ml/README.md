# ml/ — Match-Scoring Model (PLAN.md Phase 6)

## What's real vs. synthetic here

Everything in this directory — feature engineering (`features.py`), baselines
(`baselines.py`), training (`train.py`), and evaluation (`evaluate.py`) — is real,
production code, reused as-is by Phase 7's threshold Lambda.

`ml/data/postings.json` and `ml/data/labels.csv` are **not** real labeled data. Spec
section 3.2 asks you to manually label 150-300 *real* postings against your *own real*
resume — that step requires a human (you) and real scraped postings, and can't be
fabricated by an AI assistant. `ml/synthetic_data.py` generates a structurally realistic
stand-in instead, so the rest of the pipeline could be built and proven correct end to
end before real labels exist. `ml/evaluation_report.md`'s numbers reflect that synthetic
dataset — don't quote them as real model performance (e.g. in a resume bullet).

## How to replace the synthetic dataset with real labels

1. Let the pipeline run for a while (Phases 2-5) so real postings accumulate in
   DynamoDB with real `embedding_similarity` values.
2. Export postings from the table (e.g. a `Scan`, or via the query API once Phase 8
   exists) and write them to `ml/data/postings.json` in the same shape
   `ml/dataset.py:save_dataset` produces — a JSON array of `Posting.model_dump_json()`
   objects.
3. For each posting, judge "good fit" or "not a fit" against your real resume and write
   `ml/data/labels.csv` with columns `posting_id,label` (`1` = good fit, `0` = not).
   Aim for 150-300 labeled postings (spec section 3.2).
4. Put your real resume/preferences in a `CandidateProfile` JSON (see
   `common/candidate_profile.example.json` for the shape) instead of the bundled example.
5. Re-run:
   ```
   python -m ml.train --profile-path path/to/your_profile.json
   python -m ml.evaluate --profile-path path/to/your_profile.json
   ```
   `ml/evaluation_report.md` and `ml/artifacts/reranker.joblib` are regenerated from your
   real data — nothing else in the pipeline changes, since every downstream script reads
   the same `ml/dataset.py` file format regardless of where the data came from.

To regenerate the synthetic demo dataset itself (e.g. after changing
`ml/synthetic_data.py`):
```
python -m ml.generate_synthetic_dataset
```

## Design notes

- **Features** (`features.py`) are shared between training and Phase 7's inference
  Lambda by import, not duplicated — this is what prevents training/serving skew (the
  model's learned weights only mean something if inference computes features the exact
  same way training did).
- **Three approaches are compared** on the same held-out test split (`ml/dataset.py:
  split_dataset`, stratified, fixed random state so train.py and evaluate.py always
  agree on which postings are held out):
  - Keyword/BM25 (`baselines.py:bm25_scores`)
  - Embedding similarity only (`baselines.py:embedding_baseline_scores`, reusing Phase
    4/5's `embedding_similarity`)
  - Embedding + re-ranker (a classifier trained on 6 engineered features, one of which
    is `embedding_similarity` — this is literally "embedding similarity plus
    everything else")
- **Both logistic regression and XGBoost are trained**; whichever scores higher
  ROC-AUC on the held-out test set is packaged. The packaged joblib artifact is
  self-describing — it bundles `feature_names` alongside the model — so Phase 7's
  Lambda doesn't need to separately know the expected input column order.
- `ml/data/postings.json`/`labels.csv` and `ml/evaluation_report.md` are committed —
  they're small, deterministic (fixed seed), and let anyone browsing the repo see the
  pipeline's output without running anything. `ml/artifacts/*.joblib` (the trained model
  binary) is gitignored and regenerated by `python -m ml.train` instead, since a
  built model artifact isn't something to version in git.
